Learning playbook · lab/digital-campus

Learn full-stack from Digital Campus

This is a real, working college app. A senior developer built it with a classic setup: a separate backend server, a database and a frontend app. You've built Next.js clones, so you already know React and pages. This playbook explains everything else as it comes up: what each term means, why it's needed, and where it lives in the code. It ends with the places where the senior got it wrong, because learning from mistakes is half the value.

Start here

How to use this page.

  • Teal boxes explain one concept. Each says what it is, why it exists, and how it compares to Next.js.
  • Dashed boxes are hands-on experiments. Run the app and break things on purpose; that's how this sticks.

Concept

Frontend, backend, database: three separate programs

In Next.js, your pages and your app/api routes live in one project, and it feels like a single program. This project splits them:

• Frontend (web/): React code that runs in the browser and draws the screens.
• Backend (server/): a Node.js program that receives requests, checks permissions and talks to the database.
• Database: PostgreSQL, a separate program that stores the data on disk.

Why split? The same backend can later serve a mobile app (they plan a Flutter app). Each part can also be tested on its own. The cost is more wiring, which you'll see below.

What the app does

Know the product before reading the code; the code makes sense only once you know what it's for. The full spec is lab/Digital_Campus.md.

Class space official

  • A teacher creates a class (a batch of students) and invites students by email.
  • A CR (class representative, a student) keeps the class board up to date: timetable, syllabus, exam dates, notices, files.
  • Teachers post announcements and take attendance.
  • Students see a "Today" screen: next class, attendance %, upcoming deadlines.

Commons students only

  • A board where students post Ask, Gig, Market, Lost or Found.
  • Projects and challenges to build things together.
  • A people directory and message requests, which the receiver can ignore.
  • Teachers are blocked from all of it, enforced by the server.

Concept

Authentication vs authorization

Authentication asks "who are you?" (logging in). Authorization asks "are you allowed to do this?" (a teacher opening the Commons gets a 403 Forbidden).

Lesson: hiding a button in the UI is not authorization. Anyone can send the request with curl. This project checks permissions on the server for every request, which is the correct way.

Concept

SPA (single-page application)

The browser downloads one HTML file and a bundle of JavaScript once. After that, clicking links doesn't load new pages from the server: React swaps components and fetches JSON from the API.

Why here? This is a logged-in app with no need for SEO, so server-side rendering adds little. An SPA is simpler to host. It can be served by the same Express server as the API.

Concept

ORM (Object-Relational Mapper)

Databases speak SQL (SELECT * FROM "User" WHERE email = $1). An ORM lets you write db.user.findUnique({ where: { email } }) in TypeScript and translates it to SQL. Prisma also generates types from your schema, so user.emial becomes a compile error.

Where: the schema is server/prisma/schema.prisma and the client is server/src/lib/db.ts.

Concept

Validation, and why one schema for two jobs is clever

Never trust data from the browser; anyone can send anything. A zod schema like z.object({ email: z.email(), password: z.string().min(8) }) checks it before your code runs.

The trick here: server/src/lib/openapi.ts has a route() function that takes the zod schema and both validates requests and writes the API documentation from it. The frontend types are then generated from that documentation (npm run gen:api). One source of truth means the docs, the validation and the frontend types can't disagree.

Example: a CR adds an exam to the class board.

  1. Browser. The React form calls api.POST('/classes/{id}/board', { body }) from web/src/api/client.ts. The request carries the login cookie automatically.
  2. Vite proxy (dev only). The page is served from port 5173 but the API is on 3000. Vite forwards any /api/... request to port 3000.
  3. Middleware. Express parses the JSON body (max 1MB), reads cookies and the device ID header.
  4. Guard. classAccess('id','board') looks up the session from the cookie, loads the user, and checks that they're the CR or class teacher of this class. Otherwise it returns 401 or 403.
  5. Validation. zod checks the body shape. Bad input gets 422.
  6. Handler. In one database transaction it inserts the board item, writes an audit log row and creates notifications for students.
  7. Response. JSON comes back. TanStack Query invalidates the board cache, so the list refetches and shows the new exam.

Concept

What is a proxy?

A proxy is a middleman server: you send your request to it, it forwards the request to the real server, and passes the answer back.

This project meets proxies in two places:

• Dev proxy (Vite): browsers block a page on localhost:5173 from freely calling localhost:3000 (that's CORS, see the glossary). Vite forwards /api calls, so the browser thinks everything is on one origin and no CORS setup is needed.

• Reverse proxy (production): hosting platforms like Render or Fly, and web servers like Caddy or Nginx, sit in front of your Node app. They handle HTTPS certificates, then forward traffic to it. It's called reverse because it acts on behalf of the server, not the user.

Next.js note: Vercel does this for you invisibly, which is why you've never had to think about it. Mistake #1 shows what happens when you forget a proxy is there.

Concept

Middleware

A function that runs on a request before your route handler, and can modify the request or stop it. Express runs them in the order you call app.use(). Look at server/src/app.ts lines 55–70: JSON parser, cookie parser, device ID, then routes, then the 404 handler, then the error handler.

Concept

Database transaction

A group of database writes that succeed or fail together. If the audit log insert fails, the board item insert is rolled back too, so you never end up with half-saved data. In Prisma: db.$transaction(async (tx) => { … }).

Concept

Environment variables (.env)

Settings that change between your laptop and production, such as the database address, mail server and secret keys, live outside the code in a .env file. .env.example is committed with safe defaults; the real .env is git-ignored so secrets never reach GitHub. server/src/config.ts validates them with zod at startup, so a typo crashes immediately instead of failing later.

Next.js note: it's the same idea as your .env.local.

Backend concepts

Most of what makes this a "real" backend lives in server/src/lib/auth.ts. Each concept below points at where it's implemented.

Concept

Password hashing (scrypt)

Never store passwords. Store a hash: a one-way scramble that can be checked but not reversed. scrypt is deliberately slow, so an attacker who steals the database can't try billions of guesses per second. A random salt per user means two users with the same password get different hashes.

Nice detail: if someone logs in with an email that doesn't exist, the code still runs scrypt against a dummy hash. That way the response takes the same time either way, and an attacker can't tell which emails are registered by timing it. (auth/routes.ts:55)

Concept

Sessions vs JWT

After login, the server must remember you. Two common ways:

• JWT: the server hands you a signed token containing your user ID. It can't easily be revoked before it expires.
• Session token (used here): the server hands you a random string and stores its hash in a LoginSession table. Each request looks it up. Logging out or disabling a user just deletes the row, which takes effect instantly.

Where: startSession and authenticate in lib/auth.ts. The browser gets the token in an httpOnly cookie, which JavaScript can't read, so an XSS bug can't steal it. A mobile app would send it as a Bearer header instead.

Concept

CSRF (cross-site request forgery)

Cookies are sent automatically. So if you're logged in and visit evil.com, that site could submit a hidden form to this app, and your browser would attach your cookie. The defence here: for any write, the server checks that the Origin header matches the app's own URL (lib/auth.ts:108). sameSite: 'lax' on the cookie adds a second layer.

Concept

Guards (authorization middleware)

Small functions put in front of routes: auth() (logged in), staff() (a teacher), admin(), commons() (students and admins only), and classAccess(param, need), which checks your role in that specific class.

router.post('/:id/board', classAccess('id', 'board'), validate(body), handler)

Why it matters: the permission rule sits next to the route and can't be forgotten. test/wall.test.ts then calls every route as 9 different users and checks who gets in. A new route without a rule fails the test. Copy this idea into your own projects.

Concept

Rate limiting

Limits how often someone can hit an endpoint, e.g. at most 10 login attempts per 15 minutes for one IP + email. Without it, a bot can guess passwords forever. This project hand-wrote a simple limiter that counts requests in a JavaScript Map in memory (lib/auth.ts:186).

Catch: it counts by IP address. Behind a proxy, every user has the proxy's IP. See Mistake #1.

Concept

Signed URLs (HMAC) for file uploads

Instead of streaming files through API logic, the app gives the browser a short-lived upload URL like /files/local/key?exp=…&sig=…. The sig is an HMAC: a fingerprint of the URL made with a secret key only the server knows. Change one character and the signature no longer matches. It's the same pattern Amazon S3 uses ("presigned URLs").

Extra checks here: each upload URL works once, the size must match, and the file's first bytes ("magic bytes") must match its extension, so a .exe renamed to .pdf is rejected.

Concept

Cron jobs

Code that runs on a clock, not in response to a request. server/src/jobs.ts uses node-cron:

WhenJob
07:00Remind students of exams and deadlines 3 and 1 days away
07:05Warn about Commons posts expiring soon
07:10Warn students whose attendance is below the minimum
03:00 / 03:10Delete stale invites, old notifications, expired sessions

Testable trick: each job takes now as a parameter, so tests can pretend it's any date.

Concept

Race conditions and how they're handled

A race condition is when two requests arrive at the same moment and both pass a check. For example, two clicks both use the same one-time invite link. Fixes used here:

• Conditional update: "mark used where not yet used". Only one request can win.
• Unique index: the database itself refuses duplicates (Prisma error P2002, mapped to HTTP 409).
• Advisory lock: a named lock in Postgres, so only one request at a time can open an attendance session for a lecture.

Concept

Migrations

When you change schema.prisma, the real database must change to match. A migration is a saved SQL file that does exactly that change (add a column, create a table). They run in order, so every database ends up identical. This repo has 6 in server/prisma/migrations/.

Commands: prisma migrate dev creates one while developing; prisma migrate deploy applies pending ones in production.

Concept

Seeding

Filling the database with starting data. prisma/seed.ts wipes everything and inserts a fake college: teachers, classes of 30 students, a timetable, Commons posts. Every account's password is campus123. It refuses to run against production unless told to, which is good protection.

Concept

Soft rules that make data trustworthy

• Never hard-delete users. Deleting an account anonymises it, so attendance history still adds up.
• Audit log. Every admin or board change stores who did it, plus the before and after values.
• Partial unique index. A raw SQL rule says "only one active term per class", enforced by the database itself.

The API

145 endpoints under /api/v1, grouped by feature. Open http://localhost:3000/api/v1/openapi.json while it runs to see them all.

Concept

REST in 30 seconds

URLs name things, HTTP methods say what to do with them: GET reads, POST creates, PATCH edits part, PUT replaces, DELETE removes. Status codes report the result: 200 ok, 401 not logged in, 403 not allowed, 404 not found, 409 conflict, 422 invalid input, 429 too many requests, 500 server bug. The /v1 lets them change the API later without breaking old clients.

Concept

Pagination with cursors

Lists don't return everything at once. You ask for 20, and the response includes a cursor (a bookmark). Send it back to get the next 20. Unlike ?page=3, results don't shift when new items are added in between.

Concept

Route loaders as login guards

In web/src/router.tsx, each area (/s, /t, /a) has a loader: a function React Router runs before showing the page. It fetches the current user. No user means a redirect to /login; wrong role means a redirect to /403.

Next.js note: it's like a redirect in middleware.ts, but it runs in the browser. The real protection is still the server guards; this one is only for user experience.

Concept

TanStack Query: server state

"Server state" is data that lives on the server and that you hold a copy of. TanStack Query fetches it, caches it under a key like ['classes', id, 'board'], and refetches it when it's stale (30s here) or the window regains focus. After a write you call invalidateQueries(['classes', id]), and everything under that key refreshes.

const board = useQuery({ queryKey: ['classes', id, 'board'],
  queryFn: () => unwrap(api.GET('/classes/{id}/board', { params: { path: { id } } })) });

Concept

A typed API client from generated types

web/src/api/schema.d.ts (10,000+ lines) is generated from the server's OpenAPI spec; nobody writes it by hand. api/client.ts uses it so that api.POST('/classes/{id}/board', …) autocompletes the URL and type-checks the body and response. Rename a field on the server, regenerate, and the frontend shows compile errors where it breaks.

Concept

Polling instead of WebSockets

For "live" updates the app simply re-asks the server every few seconds: the attendance check-in list every 2s, chat every 5s, notifications every 30s. WebSockets keep a connection open and push instantly, but they're harder to run and scale. For a college app, polling is a sensible, boring choice.

Concept

PWA (progressive web app)

A website that can be installed like an app, with a home-screen icon and full-screen display. A service worker (a background script) caches the app's files so it opens fast. This one caches only the UI, not data, so it doesn't truly work offline.

Concept

Styling with CSS tokens

No Tailwind. Plain CSS files with design tokens, CSS variables like --primary and --s4 (spacing), in styles/style.css. The student area is indigo and the teacher area navy, switched by setting a class on <body>.

How it was built

An unusual workflow worth knowing about: the senior used AI agents as a team.

The senior wrote a plan, split it into 114 small task files (tasks/), and ran Claude sessions as an "orchestrator". Each session read INDEX.md (the status board) and the last handoff note (handoff/S01…S12), gave one task to each AI subagent, checked the result, committed it as TASK-ID: summary, and wrote a new handoff for the next session.

S01Plan only: 13 architecture decisions, docs, 78 tasks
S02–04Monorepo, Express and React skeletons, database schema. Docker didn't work, so embedded Postgres was used instead.
S05–08Auth, invites, attendance, Commons, admin. Backend complete.
S09–11All the screens. Checked only with types and curl, never in a browser.
S12Permission test, browser QA, security self-review, 16 follow-up fixes
Takeaways for you: small tasks, one commit per task, and written handoffs make big projects manageable, with or without AI. But "it compiles and the tests pass" isn't "it works": nobody opened the UI in a browser until the last session, and bugs piled up unseen.

What the senior got wrong

Seniors make mistakes too. Items marked verified were checked directly in the source code. For each one: what happened, the concept behind it, and the fix. These are great practice tasks.

verified · #1

Forgot the proxy: rate limiting would lock out the whole campus

What
The login limiter counts attempts per IP address (req.ip), but the code never tells Express it runs behind a proxy. Nowhere does it set app.set('trust proxy', …).
Concept
In production, a reverse proxy forwards every request, so to Express every request seems to come from the proxy's IP. The real user's IP is in an X-Forwarded-For header, which Express ignores unless told to "trust" the proxy. Result: all 2,000 students share one limit of 300 logins per 15 minutes. One attacker making 300 bad attempts locks everyone out.
Fix
app.set('trust proxy', 1) (the number of proxies in front), ideally from an env var. Don't use true: then anyone could fake their IP by sending the header themselves.
Lesson
Your code behaves differently behind infrastructure. Always ask: what sits between the user and my server?
verified · #2

Production start never sets NODE_ENV

What
npm start runs node dist/index.js. app.ts:63 serves the frontend only when NODE_ENV === 'production', but nothing sets it, and it's not listed in .env.example.
Concept
NODE_ENV is the convention telling Node code "this is dev" or "this is prod". Here it switches serving the UI, a safety guard on the seed script, and whether emails (with login links) get printed to logs. Missing it in production means a 404 on every page, secrets in logs, and a seed script that could wipe the real database.
Fix
Set NODE_ENV=production in the start script, run prisma migrate deploy before starting, and refuse to start in production if COOKIE_SECURE is false. The docs say start runs migrations; it doesn't.
Lesson
Test the production build before calling a project done. It was tried once, failed, and was never retried.
verified · #3

Every server error turns into "Something went wrong"

What
unwrap() in api/client.ts throws a plain object {code, message}. The catch blocks in FormSheet.tsx:48 and about 6 other places check err instanceof Error, which is always false for a plain object, so they show the generic text.
Concept
In JavaScript you can throw anything, but only objects created by new Error() (or a subclass) pass instanceof Error and carry a stack trace. Convention: always throw Errors.
Fix
class ApiError extends Error { constructor(public code: string, message: string) { super(message); } }
// in unwrap: if (r.error) throw new ApiError(r.error.code, r.error.message);
One fix in one shared function repairs every form. There's a local workaround in Compose.tsx, which shows the bug was noticed once but patched in one place instead of at the root.
Lesson
When you find a bug, fix it where all callers pass through, not just where you saw it.

Removing a student leaves a dangling reference

What
DELETE /classes/:id/members/:userId deletes the membership row but leaves User.homeClassId pointing at the old class. The student still shows the old class, and can't be re-invited elsewhere because the email is flagged as a duplicate.
Concept
Denormalised data: the same fact ("which class is this student in") is stored in two places. Every write must update both, or they drift apart.
Fix
In the same transaction, tx.user.update({ where: { id: userId }, data: { homeClassId: null } }), plus a test for it.
#5

No security headers

What
The server sends none of the standard protective HTTP headers.
Concept
Headers like Strict-Transport-Security (always use HTTPS), Content-Security-Policy (which scripts may run), and frame-ancestors (stop other sites putting your app in an invisible iframe, called clickjacking) tell the browser to add protections. Vercel and Next.js set some of these for you; plain Express does not.
Fix
Add the helmet package (one line: app.use(helmet())) or a small middleware that sets them.
#6

File storage only works on one machine

What
Uploads are saved to the server's local disk. The S3 (cloud storage) driver is a stub that throws "not installed". The URL-signing key is random on every restart, so old file links break.
Concept
Most hosting platforms have ephemeral disks: files vanish on every redeploy. Real apps put files in object storage (S3, Cloudflare R2). Secrets used for signing must be fixed values from env vars.
Fix
Add a FILE_SIGNING_SECRET env var and write the S3 driver.
#7

Memory that doesn't survive scaling

What
Rate-limit counters, used-upload signatures and cron jobs all live inside the single Node process.
Concept
If you run 2 copies of the server for more capacity (horizontal scaling), each copy has its own memory. Limits double, and every 7am reminder is sent twice. Shared state belongs in the database or Redis.
Fix
Fine for one college. Write it down as a known limit and move the state to Postgres or Redis before scaling.
#8

Slow emails inside a request

What
Inviting 500 students sends 500 emails one by one before the request answers. That can take minutes. If email fails halfway, the user sees an error even though the students were created.
Concept
Slow side-effects belong in a background job queue: save the work, respond fast, and send emails separately with retries.

Frontend gaps

What

#10

Code-hygiene slips

What
• A shared lib/dates.ts exists, yet about 10 files write their own date helpers. One uses UTC, so "today" is wrong in India before 5:30am.
• Some rules are checked in code but not enforced by database constraints (e.g. one report per user per post), which allows race conditions.
• No ESLint, no CI, and no git remote: all 141 commits live on one laptop.
• ARCHITECTURE.md describes libraries that were never installed.
Lesson
Before writing a helper, search the codebase for one. Let the database enforce rules. Push your code somewhere today.

…and what the senior got right (copy these)

  • One zod schema drives validation, docs and frontend types.
  • Server-side guards on every route, plus a test that tries every route as every role.
  • Transactions, audit logs, and race-safe "update where not used" for one-time tokens.
  • Pure logic (attendance %, clash detection) lives in separate files, so it can be tested without a database.
  • Deliberate shortcuts are marked with ponytail: comments that say what limit they have.

Glossary

Every term in one place.

Advisory lock
A named lock in Postgres that your code takes, so only one request at a time does a certain thing.
Audit log
A table recording who changed what, with before and after values.
Bearer token
A login token sent in the Authorization: Bearer … header; used by mobile apps instead of cookies.
CI
Continuous integration: a server (e.g. GitHub Actions) that runs your tests on every push.
Cookie (httpOnly)
Small data the browser sends with every request. httpOnly means JavaScript can't read it, which protects it from XSS.
CORS
A browser rule that blocks a page on one origin (domain + port) from reading responses from another, unless the server allows it.
Cron
Running code on a schedule, e.g. every day at 07:00.
CSRF
A trick where another site makes your browser send a request with your cookie. Blocked here by checking the Origin header.
Dry run
Doing all the checks but saving nothing, to preview the result.
Env var
A setting passed to the program from outside the code (.env).
Hash / salt
A one-way scramble of a password; the salt is random data mixed in so equal passwords hash differently.
HMAC
A signature made with a secret key that proves a URL or message wasn't changed.
Idempotent
Doing it twice has the same effect as once. Opening the same attendance session twice returns the same session.
Magic bytes
The first bytes of a file that identify its real type (PDFs start with %PDF).
Middleware
A function that runs before route handlers and can modify or stop the request.
Migration
A saved, ordered database change script.
Monorepo
One repository containing several packages (here server and web).
OpenAPI
A standard JSON format describing every endpoint of an API; tools generate docs and types from it.
ORM
A library that maps database tables to code objects (Prisma).
Proxy / reverse proxy
A middleman server that forwards requests. Reverse proxies sit in front of your app in production and handle HTTPS.
PWA
A website installable like an app, using a service worker for caching.
Race condition
A bug where two simultaneous requests both pass a check that should only let one through.
Rate limiting
Capping how many requests someone can make in a time window.
Seed
A script that fills the database with starting or demo data.
Session
The server's record that a token belongs to a logged-in user.
SPA
A single-page application: one HTML page; React handles navigation in the browser.
SMTP
The protocol for sending email.
Transaction
A group of database writes that all succeed or all fail.
trust proxy
An Express setting that makes it read the real client IP from X-Forwarded-For.
XSS
Cross-site scripting: an attacker getting their JavaScript to run on your page.
zod
A TypeScript library for describing and validating data shapes.
